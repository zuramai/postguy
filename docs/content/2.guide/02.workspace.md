title: Workspace
description: A workspace is a folder of JSON files. How it is chosen, locked, saved, restored and exported.

A workspace is one folder. Everything you create (collections, environments, globals, history, cookies, settings) lives inside it as plain files. There is no account, no database and no cloud copy. Back it up or version it like any other folder.

## Choosing a workspace

The workspace is chosen when Postguy starts, in this order:

1. `postguy --workspace DIR`
2. `./postguy-workspace`, if that folder exists in the launch directory
3. `~/postguy-workspace` (`%USERPROFILE%\postguy-workspace` on Windows)

The folder is created on first use. There is no in-app workspace switcher: to use another workspace, quit and start Postguy with a different `--workspace`. The header shows the folder name.

If the workspace cannot be opened (for example a permission error), the window opens without it and the status text at the bottom right shows the error.

::note
An installed app often starts in a read-only folder, which is why the default is your home directory and not the launch directory. See [Installation](/getting-started/installation#where-your-data-lives).
::

## What is inside

Opening a workspace creates `collections/`, `environments/`, `protos/`, `files/`, `.trash/` and `.postguy/`. Postguy's own settings and session live in `.postguy-config/`. The complete tree, file schemas and read limits are in [Workspace format](/reference/workspace-format).

| Path | Purpose |
|---|---|
| `postguy.json` | Workspace metadata: schema `postguy/workspace/1`, collection and environment order, active environment. |
| `collections/<id>.json` | One file per collection, including folders and requests. |
| `environments/<id>.json`, `globals.json` | Variables. Values of secret variables are not in these files. |
| `files/` | The default working directory for file bodies and `Save Response`. |
| `assets/<collection id>/` | A collection's [assets](/guide/collections#assets). |
| `history.jsonl` | The send history. |
| `.trash/` | Deleted items. |
| `.postguy/` | Secrets, cookies, cached response bodies, stored runs, the lock file. |
| `.postguy-config/` | `settings.json` and `session.json`. |

## Saving

Every file is written atomically: Postguy writes a temporary file in the same folder, then renames it over the old one, and keeps the previous version as `<file>.bak` (one generation). A failed save leaves the old file in place.

If a file cannot be parsed when it is loaded, it is renamed to `<file>.corrupt-<time>` and Postguy continues without it and reports it. Nothing is deleted. Corrupt `settings.json` falls back to defaults; a corrupt `session.json` starts a fresh session.

Environment and collection edits autosave shortly after you stop typing. A request is saved with `Save` or `Cmd/Ctrl+S`; the dot on its tab shows unsaved changes.

## The workspace lock

Only one process can open a workspace at a time. Postguy writes `.postguy/lock` containing the process id and a start time, and removes it on a clean exit.

- If another live process holds a fresh lock, opening fails with `workspace already open by pid N; close that instance or remove <path> if it is gone`.
- A lock whose process is gone, or whose start time is more than 3 minutes old, is taken over.

The lock is not renewed while Postguy runs, so it is a guard against accidental double opens and not a hard guarantee: a second process that starts more than 3 minutes after the first can take the lock over. Do not open the same workspace in two processes at once.

The lock is shared by the app, `postguy-cli` and the [automation tools](/reference/automation-tools), so close the app before running the CLI against the same workspace. See [Troubleshooting](/getting-started/troubleshooting).

## Trash

Deleting a collection or environment moves its file to `.trash/` together with a small metadata file (original path, kind, deletion time) and removes its secrets. The `Trash` tab (bottom bar, or the command `Open trash`) lists those entries with `Restore`. A restore puts the file back at its original path, or adds ` restored` to the name when that path is taken.

Deleting a folder or request writes a record to `.trash/item-<time>.json` containing the item, its collection id and the deletion time. The `Trash` tab does not list these records yet; recover one by copying the `item` value from that file back into the collection by hand.

::warning
The trash is never emptied by Postguy today. The 30-day retention window (`DEFAULT_RETENTION` in `crates/store`) is defined, but nothing calls the purge. Delete files from `.trash/` yourself if you want them gone.
::

Collections and folders ask you to type `delete` before they are removed. Requests and environments are removed immediately (they still go to the trash).

## Undo

`Cmd/Ctrl+Z` in the sidebar undoes the last rename or move of a tree item, and `Cmd/Ctrl+Shift+Z` redoes it. Deletes are not undone this way: use the trash.

## Session restore

Postguy saves the open tabs, the sidebar section state and heights to `.postguy-config/session.json`, at most once a second and only when something changed. On the next start:

- the tabs are restored, and tabs whose collection, request or environment no longer exists are closed with a status note;
- after an unclean exit the status text says `Session restored after an unexpected exit`.

Window position and size, expanded folders and the two-pane toggle are not restored.

## Secrets

A variable marked `Secret` keeps only its name in the environment, globals or collection file. The value is stored in `.postguy/secrets.json` (mode 0600 on Unix) and loaded back into memory when the file is read. OAuth 2.0 access and refresh tokens are stored there too. Deleting an environment or a collection removes its secrets.

Secret values are masked in history, the console and generated snippets, and left out of exports unless you choose to include them.

::warning
`.postguy/secrets.json` is not encrypted at rest. Anyone who can read your workspace folder can read your secrets. Keep it out of version control and backups you share. OS keychain storage is not implemented.
::

## History

Each send from the request builder is appended to `history.jsonl`, one JSON object per line. Collection runs do not write history. The file is capped at 5000 entries: when it grows past that the oldest entries are dropped. See [HTTP requests](/guide/http-requests#history-and-console) for what an entry stores. `Save response bodies in history` (Settings › General) additionally caches each response body under `.postguy/responses/`.

## Export and restore

To back up a workspace, copy the folder. For a portable archive, use the command `Export all workspace data…`, which writes a zip (default name `Workspace.zip`). The zip holds the collections, environments, globals, `protos/`, `files/`, `assets/`, `history.jsonl` and `postguy.json`. It leaves out everything whose path starts with `.postguy` (secrets, cookies, cached responses, runs, lock, and `.postguy-config/`), `.trash/` and `.bak` files, and it skips symbolic links. It holds at most 50,000 files and 1 GiB.

Restore is documents-only: importing the zip reads only its `.json` entries (collections, environments, globals) and merges them through the normal import rules. Files such as assets and `.proto` sets are not extracted. See [Import and export](/guide/import-export#zip-files).

::tip{title="Headless"}
`workspace_open` creates or opens a workspace, `workspace_info` summarizes it, `workspace_export_zip` writes the zip, `import_zip` reads one. The `postguy-cli run --collection` command takes `--workspace DIR`. All of them need the workspace lock, so the app must not have it open. See [Automation tools](/reference/automation-tools).
::
