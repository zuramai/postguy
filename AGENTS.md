# AGENTS.md: rules for every agent and contributor

These rules bind every AI agent and every human contributor working in this repository. They come before any task, instruction or deadline. This is the only rules file; there is no separate `CLAUDE.md`. `PROMPT.md` is the product brief (what to build, architecture, milestones). If `PROMPT.md` and this file disagree, **this file wins.**

Postguy is a clean-room, offline, Rust-native API client (HTTP, gRPC, WebSocket) built with egui, targeting the essential offline features of Postman. It runs natively on macOS, Windows, Linux and FreeBSD. There is no web (WASM) build.

---

## 1. Asset policy (absolute, no exceptions)

An **asset** is any non-code material that the project includes, ships, embeds, generates for publication, or shows in its documentation. This covers:

- icons, images, illustrations, screenshots and logos;
- fonts;
- binary data files;
- sounds and video;
- sample, demo and test collections, protos, OpenAPI files, word lists and other documents that are committed or published;
- anything the app renders from those.

### 1.1 Nothing from Postman products

- **Never** use icons, images, artwork, logos, UI graphics, fonts, stamps, cursors, brand colours, illustrations, marketing copy or sample collections taken from a Postman product, installer, website, document or package.
  - "Postman product" includes the Postman app, Postman web, Postman CLI, Newman, Postbot, the Postman Learning Center and the Postman API Network.
  - This holds even when Postman publishes the material under an open licence, if it is **visual design or content**. Postman's code and schema repositories (for example Newman, `postman-collection`, `postman-sandbox`) are not a design or behaviour source either (see section 2).
- **Never** recreate, trace, redraw or closely imitate a Postman icon, logo, mascot or illustration. Our icons come from Lucide, and our visual design (palette, spacing, layout details) is our own. Postman's information architecture (sidebar, tabs, request builder, response viewer) is behaviour, not artwork, and we may follow it.
- Screenshots of Postman exist only as private, local observation notes under `plan/postman/`, which is gitignored (the starting screenshots in `prompt_images/` belong there too). They must **never** be committed, published, linked, shown in docs, used as a design source to trace, or placed anywhere else in the repository or its outputs.
- The only Postman-authored material allowed is **non-visual technical data** that is openly licensed and required for file compatibility. Each item needs its own entry in `ATTRIBUTION.toml` with `postman_data = true`, and the list below is closed:
  - The Postman Collection Format JSON schemas (v2.0.0 and v2.1.0, Apache-2.0), vendored only as test data to validate our imports and exports.

  Adding anything to this list needs the owner's explicit approval.

### 1.2 Only open, provable licences

Every asset must be one of:

- **Open source:** ISC, MIT, BSD-2-Clause, BSD-3-Clause, Apache-2.0, OFL-1.1, Ubuntu-Font-1.0 or Bitstream-Vera.
- **Creative Commons:** CC0-1.0, CC-BY-4.0 or CC-BY-SA-4.0.
- **Public domain.**
- **Contributor-original:** created or generated by a contributor who owns it and licenses it under the project licence (`MIT OR Apache-2.0`). This is the category for the app icon and logo, demo collections, test protos and word lists.

Anything else is forbidden, including assets whose licence you cannot prove from the source. Examples:

- system fonts (Apple, Microsoft, Google Android system UI fonts that are not openly licensed);
- emoji artwork from Apple, Microsoft or Samsung;
- stock photos and illustrations;
- "free for personal use" material;
- screenshots of other people's software.

**Screenshots of Postguy** are contributor-original. Everything visible in them must itself be allowed: our UI, Lucide icons, allowed fonts, and demo data written for this project. Never screenshot a real user's collections, tokens or responses.

### 1.3 Every asset is attributed

- **`ATTRIBUTION.toml`** (repo root) is the single source of truth. It has **one entry per asset file**, whether committed, vendored, generated at build time or bundled through a Cargo dependency (for example egui's default fonts). Each entry records:
  - path or URL, title, author;
  - source (URL, with version or commit);
  - SPDX licence, and the licence file in the repo;
  - SHA-256;
  - how it is used.
- **`ATTRIBUTION.md`** is generated from it (`cargo xtask assets --write`). Never edit it by hand.
- **`NOTICE`** keeps the licence notices that the licences require.
- **`cargo xtask assets`** runs in `cargo xtask ci`. It fails if:
  - an asset file in the repository has no entry;
  - an entry's hash does not match;
  - a licence is not on the allowlist;
  - a licence file is missing;
  - an image, icon or font names Postman as author or source.

### 1.4 Fonts

- **Never commit a font file to this repository** without the owner's decision on where fonts live. The owner has not made that decision yet, so v1 uses the default fonts that ship inside egui (listed in `ATTRIBUTION.toml` as Cargo-dependency assets).
- The desktop app may read one font **already installed on the user's machine** at runtime, as the last interface fallback for characters no embedded face has (CJK, Arabic, emoji and so on). That font is never embedded, shipped, committed or copied, and never appears in published screenshots (`POSTGUY_SYSTEM_FONTS=0`, which `cargo xtask screenshots` sets). It is not a way around section 1.2: nothing from it may enter a package or the repository.

### 1.5 Procedure for adding or changing an asset

1. Find an asset under an allowed licence from its **original source**: the author's repository or a release, not a random mirror. Record the exact version or commit.
2. Confirm the authorship. It must not be Postman (section 1.1). Keep the licence text.
3. Add the file together with its licence file, plus an `ATTRIBUTION.toml` entry. Run `cargo xtask assets --write`, then `cargo xtask assets`.
4. If an asset's origin or licence is unclear, **do not add it.** Ask the owner.

If you find an asset that breaks these rules, stop and remove it from the repository and every output, including docs, screenshots and generated files. Then tell the owner at once.

## 2. Clean-room rules

- Never read, decompile, unpack or copy anything inside the Postman app bundle (its `app.asar`, bundled JavaScript, resources). Names and directory listings only.
- Behaviour comes only from public specifications and documentation (the Postman Collection Format schema, the public Postman Learning Center, RFCs for HTTP, URI, cookies, WebSocket, OAuth, the gRPC protocol and reflection service), and from black-box observation of a real Postman install with synthetic data.
- Do not port or translate another implementation (Newman, postman-sandbox, postman-runtime, postman-code-generators, Insomnia, Bruno, Hoppscotch). They may be permissively licensed, but behaviour comes from docs, schemas and observation, not from reading their code.
- Never copy GPL/AGPL/LGPL code, and never link such a crate. Copyleft tools may run only as external oracle processes in tests (for example `curl` or `grpcurl` to cross-check output).
- Observe Postman only with synthetic data. Never capture personal data, account information, tokens, workspaces or history.
- Real-file oracles (collections exported from a real Postman) are kept local and never committed. Write our own golden files instead.

## 3. Agent control (automation and MCP)

- **Everything is reachable headlessly.** Every user-facing feature must be callable without the GUI: an engine API, then a tool in `crates/automation` (`postguy-cli run` and MCP use the same table). A feature is not done until its tool exists and has an end-to-end test (`crates/automation/README.md`, "Adding a tool").
- **The UI control channel is opt-in too.** It runs only when the app is launched with `--control <file>`. It binds to loopback, uses a fresh random token per launch, and writes it to an owner-only file. Never enable it by default, widen the bind address, or log the token.
- **The MCP server is opt-in.** Never make the app, the CLI or an installer start it, register it with an agent, or listen on a port by default. It runs only when a user (or an agent the user configured) launches `postguy-cli mcp`. Any future network transport must be off by default, bound to loopback and authenticated with a token.
- **Safe by default.** Tools must never discard unsaved work silently, must write atomically, must honour `--root`, and must return errors an agent can act on (say what was wrong and what is allowed). Every path, including ones reached by nested dispatch, is confined; a path outside the root gets the same refusal whether or not it exists.
- **Track parity honestly.** Every user-facing feature has an entry in `parity/postman-features.toml`. Mark it `shipped` only when it works end to end and the entry cites a passing test (`evidence`); `cargo xtask parity` (part of `xtask ci`) rejects claims whose commands, tools or tests don't exist. "Shipped" means exists and tested, not "as good as Postman"; say in the notes what is still missing.
- **Use it to test.** Agents should drive the engine through `postguy-cli run --script` or the MCP tools, and check the output, to verify their own changes. For UI changes, launch the app with `--control` and use `postguy-cli ui` (`inspect`, `click`, `screenshot`) to check the real interface.

## 4. Never crash

Postguy opens files from strangers (imported collections, OpenAPI documents, `.proto` files), talks to arbitrary servers, and runs users' scripts. People trust it with their work. A malformed file, a hostile response, a bad tool argument, a corrupt settings file or a full disk must produce an error the user (or agent) can act on, never a crash and never lost work. **This outranks feature work:** don't ship a feature by adding a panic path, and fix a crash before building on top of it.

- **Fail with `Result`.** Non-test code returns errors through the crate's error type and `?`. Where readers are lenient by design, fall back gracefully and record the repair in the import report or log (see Fidelity in section 5).
- **No panicking shortcuts.** No `unwrap()`, `expect()`, `panic!`, `unreachable!`, `todo!` or `unimplemented!` outside tests, unless the call is provably infallible (for example writing to a `Vec`), with a comment saying why. `assert!` only for internal invariants that input cannot reach.
- **No `unsafe`.** The workspace sets `unsafe_code = "forbid"`. If a platform API needs it, use a maintained safe wrapper crate; a real exception needs the owner's sign-off.
- **Treat every input-derived number as hostile.** Use `get()` instead of `[i]` or `[a..b]`. Slice strings only at char boundaries. Use checked or saturating arithmetic for lengths, offsets and counts. Guard against division by zero and NaN/inf casts, and never cast a negative value to `usize`. Cap allocations sized by the input (response bodies, decompressed sizes, message counts, proto and OpenAPI nesting, file sizes).
- **Bound recursion.** Object graphs can be cyclic or deeply nested (JSON, `$ref`, proto messages, variable references, redirects). Walk them with seen-sets or depth limits.
- **Don't cascade.** Handle lock poisoning, and keep a panic in a worker thread or spawned task from taking the app down. Entry points that run untrusted input (script execution, importers, command execution, file import/export) keep a last-resort `catch_unwind` guard that turns an escaped panic into an error message and keeps the user's data. Keep `panic = "unwind"` (the default) so the guard works; never set `panic = "abort"`. It is a safety net, not a substitute for the rules above.
- **Untrusted scripts are sandboxed.** No filesystem, no process, no network except through the app's own request engine, with wall-clock, instruction and memory limits. A hostile script must not hang or crash the app.
- **Prove it.** Every crash fix comes with a small synthetic regression test that panicked before the fix. Turn fuzzer findings (`cargo xtask fuzz`) into such tests before fixing them.
- **Enforced by clippy.** Root `clippy.toml` lets tests use `unwrap`/`expect`/`panic!`. A crate that is clean carries `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::unimplemented, clippy::todo, clippy::unreachable)]`; new crates start with it.

## 5. Working rules

### 5.1 Start every session here

1. Read `plan/STATUS.md` (current milestone, next unchecked task, blockers). `plan/` is gitignored and local-only. `ROADMAP.md` is the one-page summary (stage, progress log) and `docs/roadmap.md` the milestone table. At the end of every session, update the milestone row and add a line to the `ROADMAP.md` progress log.
2. Read `PROMPT.md` for the product brief, the task in `plan/execution-plan.md`, and the README of the crate you're touching. Read `docs/gaps.md` before choosing work, and prefer the ranked gaps over new P2/P3 features. Keep these documents true when things change.
3. Follow the autonomous operation protocol in `plan/execution-plan.md`: orient, plan, implement and test, verify, record, commit. Don't stop to ask unless `PROMPT.md` section 13 lists the decision as the owner's.

The machine-readable parity checklist lives in `parity/` (committed).

### 5.2 Non-negotiables

- **Assets and clean-room:** sections 1 and 2.
- **Privacy and network.** The app makes no network request the user did not initiate: no telemetry, no crash upload, no update check, no cloud sync. Never log secret variable values, client-certificate passphrases or the control-channel token. Real tokens, API keys and responses never enter the repository, tests or screenshots.
- **Rust only** in the product and the build (`xtask`). No handwritten JS/TS. User scripts run in an embedded engine, and the `pm` API is implemented in Rust. If a JS prelude seems unavoidable, stop and ask the owner.
- **Layering.** Nothing below L7 depends on egui/winit/eframe/rfd. The layer table is in `PROMPT.md` section 4.1 and is enforced by `cargo xtask layers`. Frontends reach the engine only through `crates/engine`.
- **Fidelity.** Unknown fields in imported collections, environments and settings are preserved in `extras` and written back on export. Never silently drop or repair data without recording it in the import report. Saves are atomic. A failed save leaves the previous file intact and the in-memory state dirty.
- **Offline untrusted-file handling.** Cap file sizes, nesting and expansion for every importer (Postman, OpenAPI/YAML, HAR, cURL, `.proto`, data files). File paths in requests resolve against the working directory; escaping it needs the explicit setting.
- **Review every update as you make it, at four zooms.** Not an end-of-task pass; a per-update habit, so a defect never gets built on.
  - **Clause:** checked arithmetic, `get()` not `[i]`, char-boundary slicing, the right error through `?`, `<` against `<=`, 0-based against 1-based seams, capped allocations.
  - **Function:** is it total (name an input that panics; walk empty, zero, max, malformed, cyclic); is the return type honest.
  - **File/module:** two sources of truth, dead or duplicated code, is the public surface still smallest and the doc comment still true.
  - **Project:** layering, undo/redo and dirty tracking, save fidelity, session restore, `--root` confinement, a matching `automation` tool, and whether a `parity/` status or note just became untrue.
  - Scale the zoom to the change, and fix what a level turns up before widening. Tests mirror the zooms: property, unit, crate integration, end-to-end.
  - **Prove a test fails before the fix by actually reverting the fix.** A test nobody has seen fail is not evidence.
  - **Rebasing is a review step, not a mechanical one.** Read every hunk you resolve, and the auto-merged hunks in the files you touched too.
- **External PRs are held to safety, security and completeness before style.** Provenance first (no Postman-derived asset, no committed font, no copied GPL/AGPL code, behaviour from specs and docs and not from reading another implementation), then no new panic path or `unsafe`, then `--root` confinement on every path including nested dispatch, opt-in-only MCP and control channel, no new outbound network, then a headless `automation` tool, tests at the right zoom and an honest `parity/` entry. Provenance is the part a contributor cannot be expected to know, and the only part that cannot be undone after merge.
- **Dependencies.** Permissive licences only (`deny.toml`; `cargo xtask deny`). Always `default-features = false` and enable only what is used. No dependency on `craft-ui`, `craft-libs` or other storytold-internal repositories. Anything outside the allowlist, or anything that adds unrequested network traffic, needs the owner's approval.
- **Size and speed are requirements.** The budgets in `PROMPT.md` section 8 are enforced by `cargo xtask size` and `cargo xtask bench`. Never add a repaint loop. Never run I/O, parsing, formatting, searching or scripts on the UI thread.

### 5.3 Quality gates

Before every commit: `cargo fmt --check`, clippy with `-D warnings`, the tests, `cargo xtask layers`, `cargo xtask assets`.

- **Scope builds and tests to the crates you touched**: `cargo clippy -p <crate> -j 2 --all-targets` and `cargo test -p <crate> -j 2`, under a `timeout`. A full `--workspace` build can lock up a development machine's CPU; it is CI's job and CI runs it on every PR. Run the workspace sweep locally only when you have a reason to and the machine is free.
- Tests are hermetic: they never touch the internet. They use the loopback servers in `crates/testkit` (HTTP, TLS, OAuth token endpoint, gRPC with our own `echo.proto`, WebSocket).

### 5.4 Commits and PRs

`main` is the only integration branch and is **never pushed to directly**. Branch from an up-to-date `main` as `<type>/<slug>` (`feat/`, `fix/`, `docs/`, `chore/`, `refactor/`), one task id per commit (for example `M2.3: redirect loop with cookie capture`), commit only green states, and open a PR into `main` using `.github/pull_request_template.md`. Merge only when CI is green. Rebase your own branch the same day `main` moves under it, and ask the author to rebase theirs; never rewrite a contributor's branch. Conflict risk tracks how contested the files are: tooling, tests and docs are nearly free, while `ui-egui` and shared widgets are where several people collide at once.

### 5.5 Running and looking at the app

- `cargo run -p postguy` opens the desktop app (`--workspace DIR` picks a workspace folder).
- `cargo run -p postguy-cli -- run --script steps.json --root DIR` drives the engine headlessly through the automation tools (`postguy-cli tools` lists them). Use it to check engine changes. `postguy-cli mcp` is the opt-in MCP server (section 3).
- `cargo xtask fuzz --time 300` mutation-fuzzes the importers, URL and cookie parsers, filters, the variable resolver and the script sandbox in child processes. Findings land in `fuzz-out/` (git-ignored; never commit corpus-derived files). Turn every real finding into a small synthetic regression test before fixing it.
- `cargo xtask parity [--partial]` reports progress from `parity/postman-features.toml`. Update the entry when a feature ships.
- `cargo xtask size` and `cargo xtask bench` check the binary-size and performance budgets.
- For UI work, **look at the result**. Either launch `postguy --control FILE` and use `postguy-cli ui --control FILE screenshot --out x.png` (plus `inspect`, `click`, `key`, `type`, `command`, `set`), or take a headless shot with `cargo run -p postguy-ui-egui --example shot`. Control-channel tests use kittest (`crates/ui-egui/tests/control.rs`).
- Parallel agents: use a separate `CARGO_TARGET_DIR` per agent and separate git worktrees.
