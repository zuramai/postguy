Postguy can check for a new release, then download, verify and install it from inside the app.

## Finding a new release

- **Automatically.** At startup and then once a day, Postguy asks GitHub for the latest published release of `zuramai/postguy`. Drafts and pre-releases are never offered. Turn this off with `Settings › About › Check automatically`. The setting is stored as `checkForUpdates` in the workspace's [settings file](/guide/settings).
- **By hand.** `Help › Check for updates…`, the command palette, or `Settings › About › Check now`. These work even with the automatic check off.

When a newer version exists, an `Update` button appears in the header next to the Settings gear. It opens the update dialog with the version and the release notes. A failed automatic check (no network, for example) shows only in `Settings › About`. A check you started yourself shows its error in the dialog.

The check is one HTTPS request to `api.github.com`. It honours your [proxy and CA bundle](/guide/cookies-proxy-certificates) settings, always verifies the server certificate and never sends a client certificate. Nothing is downloaded until you choose `Download and install`.

## Downloading and verifying

`Download and install` fetches the package for your system from the release, plus the release's `SHA256SUMS.txt`.

1. The download's SHA-256 must match the line for it in `SHA256SUMS.txt`. If it does not, the file is deleted and nothing is installed.
2. If the running app is code-signed, the new one must carry a valid signature from the same signer: the same Apple Developer ID team on macOS, the same Authenticode certificate subject on Windows. A mismatch or a missing signature stops the install. The dialog says which checks ran.
3. Linux packages and unsigned builds are verified by the checksum alone.

Redirects may not leave HTTPS. Downloads are capped at 512 MiB.

When the update is ready, the header button reads `Restart to update`. Restarting saves your session, including unsaved drafts, closes the window, installs the update and opens Postguy again with the same workspace. If the install fails, the old version opens again and shows why.

## What updates itself

| Install | Package used | How it is replaced |
|---|---|---|
| macOS `Postguy.app` (DMG or zip) | `postguy-<version>-macos-universal.zip` | The app bundle is swapped in place. |
| Windows MSI | `postguy-<version>-windows-<arch>.msi` | The installer runs after Postguy closes. Windows asks for administrator rights. |
| Windows portable zip | `postguy-<version>-windows-<arch>.zip` | `postguy.exe` and `postguy-cli.exe` are replaced in their folder. |
| Linux AppImage | `postguy-<version>-linux-<arch>.AppImage` | The AppImage file is replaced. |
| Linux `.tar.gz` | `postguy-<version>-linux-<arch>.tar.gz` | `bin/postguy` and `bin/postguy-cli` are replaced. |
| Flatpak, `.deb`, `.rpm` | none | Update with `flatpak update`, your package manager or your software centre. The dialog says so. |

The folder holding the app must be writable by you. If it is not, the dialog says so; download the update from the release page instead. A build you compiled yourself cannot update itself.

Downloads wait in a per-user folder: the temporary folder on macOS and Windows, `~/.cache/postguy-update` (or `$XDG_CACHE_HOME`) on Linux. Postguy removes them a day later.

## Headless

- `update_check` returns this build's version, the latest release with its assets and whether it is an update.
- `update_download` downloads one asset into a folder inside `--root` and verifies it against `SHA256SUMS.txt`.

Installing over the desktop app is done by the app itself. See [Automation tools](/reference/automation-tools#updates).
