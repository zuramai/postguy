Everything the app can do to a workspace is available as a JSON tool, and every frontend (the CLI today, an MCP server later) shares the same table. This page lists all **71** tools. It is transcribed from the output of `postguy-cli tools --json`, which is the source of truth; run it to get the schemas in machine-readable form.

```sh
postguy-cli tools            # name, safety and title, one line per tool
postguy-cli tools --json     # {"tools":[{name,title,description,inputSchema,readOnly,destructive}]}
```

See the [CLI reference](/reference/cli) for the commands that run them.

## How calls work

- **Arguments are one JSON object.** `null` or no `--json` means `{}`. Any other JSON type is refused with "argument `(arguments)` must be a JSON object".
- **Unknown arguments are refused**, and the error lists what is allowed: ``tool: unknown argument `x`; allowed: a, b``. Every schema has `additionalProperties: false`.
- **Missing required arguments are refused**: ``tool: missing required argument `x` ``. Types are not validated up front; a wrong type fails inside the tool with a message of the form "argument `x` must be ..., got ...".
- **Error strings** are written to say what was wrong and what is allowed. The ones you will meet most:
  - ``unknown tool `x`; run `postguy-cli tools` ``
  - `no workspace is open; call workspace_open first`
  - ``collection `ID` not found in the workspace`` (the same shape for every entity kind)
  - ``PATH is outside the allowed directory ROOT``: the same text whether or not the path exists.
- **Ids** are opaque strings. Take them from the list tools (`collection_list`, `env_list`, `run_list`, ...) or from the result of a create tool. Postguy generates UUIDs; ids from imported files can be shorter.
- **Deletes go to the workspace trash.** Destructive tools are flagged `destructive` and move data to `.trash/` rather than erasing it (`history_clear`, `console_clear` and `cookies_*` clear their own stores). See [Workspace format](/reference/workspace-format).
- **Paths** in arguments (`path`, `out`, `data`, `paths`) go through `--root` confinement when a root is set: relative paths resolve against the root, and a path outside it is refused. Without `--root` nothing is confined and relative paths resolve against the current directory.
- **Response bodies are capped at 1 MiB** in tool results (`request_send`, `response_get`, `response_render_body`). The full decoded body is available through `response_save`.
- `request_send`, `request_cancel` and `collection_run` do not hold the session lock while they run, so `request_cancel` can stop an in-flight send from another thread. The CLI runs steps one after another, so this only matters for embedders.

## One call is one process

Every `postguy-cli call` starts a new process with **no workspace open**. A tool other than `workspace_open` fails with `no workspace is open; call workspace_open first`. For anything with more than one step, use `run --script`, which runs a list of steps in one process and one session.

A script file cannot pass one step's result to the next step: arguments are static JSON. Tools take ids, not names, so for name-based flows either

- import something and read the ids back with a list tool (`import_text` or `import_file`, then `collection_list`), in a second `run --script` call or by reading the printed result lines; or
- let an agent read each step's output and generate the next script; or
- use `run --collection NAME --workspace DIR`, which resolves names for you (see the [CLI reference](/reference/cli)).

### `run --script` step format

A script is a JSON array of steps, or an object with a `steps` array. Each step is `{"tool": "<name>", "args": {...}}`; `args` is optional. Steps run in order, and the first step must be `workspace_open` unless the tools you call need no workspace.

```json
[
  {"tool": "workspace_open", "args": {"path": "work"}},
  {"tool": "collection_create", "args": {"name": "Smoke"}},
  {"tool": "collection_list", "args": {}}
]
```

Output: one line per step on stdout, `{"step":0,"tool":"workspace_open","ok":true,"result":{...}}`, then `{"ok":true,"steps":3}`. A failing step prints `{"step":1,"tool":"...","ok":false,"error":"..."}` on stderr, stops the run and exits 1.

A send flow that fits in one script (after the collection and request exist, using their real ids):

```json
[
  {"tool": "workspace_open", "args": {"path": "work"}},
  {"tool": "request_send", "args": {"collection": "COLLECTION_ID", "request": "REQUEST_ID"}},
  {"tool": "response_get", "args": {}},
  {"tool": "history_list", "args": {"limit": 5}}
]
```

## Tool reference

In the tables, an argument in **bold** is required. Safety is `read-only` (never changes anything), `write` or `destructive` (deletes or clears data).

### Workspace

| Tool | Safety | Purpose | Arguments |
|---|---|---|---|
| `workspace_open` | write | Create the folder if needed and open it; takes the workspace lock. Paths stay inside --root when one is set. | **`path`** — workspace folder |
| `workspace_info` | read-only | Path, counts and the active environment id of the open workspace. | none |
| `workspace_export_zip` | write | Zip the workspace documents (not .postguy secrets/cookies/cache and not .trash); path resolves inside --root. | **`out`** — zip file path |
| `import_zip` | write | Reads .json entries (collection/environment/globals) from a zip through the normal importers; unsafe paths are refused, arbitrary entries are skipped. | **`path`** — zip file path; `replace` (boolean) — replace same-id documents instead of suffixing |

### Collections and folders

| Tool | Safety | Purpose | Arguments |
|---|---|---|---|
| `collection_list` | read-only | Collections in sidebar order with id, name and counts. | none |
| `collection_get` | read-only | The full collection JSON. | **`collection`** — collection id |
| `collection_create` | write | A new empty collection with a generated id. | **`name`** — collection name |
| `collection_rename` | write | New name; empty names are refused. | **`collection`** — collection id; **`name`** — new name |
| `collection_duplicate` | write | Deep copy with fresh ids for every item. | **`collection`** — collection id; `name` — name for the copy (default: `<name> Copy`) |
| `collection_delete` | destructive | Moves the collection file to the workspace trash and drops its secrets. | **`collection`** — collection id |
| `folder_create` | write | Inside the collection root or another folder. | **`collection`** — collection id; `parent` — parent folder id (omit for the collection root); **`name`** — folder name |
| `folder_rename` | write | New name; empty names are refused. | **`collection`** — collection id; **`folder`** — folder id; **`name`** — new name |

### Responses, cookies, history and console

| Tool | Safety | Purpose | Arguments |
|---|---|---|---|
| `response_get` | read-only | The newest (or `id`) cached response: status, headers, body (base64 plus text when UTF-8, capped at 1 MiB), size and timings. | `id` — history id (omit for the newest response) |
| `response_save` | write | Writes the DECODED body atomically to `path` inside --root. | `id` — history id (omit for the newest response); **`path`** — file path |
| `response_render_body` | read-only | Returns the body as UTF-8 text (with replacement markers when invalid) or base64, capped at 1 MiB. | `id` — history id (omit for the newest response); `format` — "text" (default) or "base64" |
| `cookies_list` | read-only | Every jar cookie with domain, path, flags and expiry, plus the script allowlist. | none |
| `cookies_set` | write | Stores one raw Set-Cookie value for a URL (domain/path/secure/expiry rules apply) and persists the jar. | **`url`** — the URL the cookie belongs to; **`setCookie`** — one Set-Cookie header value |
| `cookies_delete` | destructive | Deletes by (domain, path, name) and persists the jar. | **`domain`** — cookie domain; **`path`** — cookie path; **`name`** — cookie name |
| `cookies_clear` | destructive | Deletes every cookie and persists the empty jar. | none |
| `history_list` | read-only | The newest sends, newest last (default 50). | `limit` (integer, min 1) |
| `history_open` | read-only | One entry by id, including the as-sent request snapshot. | **`id`** — history id |
| `history_clear` | destructive | Empties history.jsonl atomically. | none |
| `console_get` | read-only | Newest-last console entries, optionally filtered by level or kind (default 100). | `limit` (integer, min 1); `level` — "info" \| "warning" \| "error"; `kind` — "request" \| "log" \| "warning" \| "error" |
| `console_clear` | destructive | Drops every retained console entry (the history file is untouched). | none |

Notes on a few arguments:

- `ws_messages` `since` and `ws_disconnect` `code` are declared as strings in the schema, but the implementation reads JSON numbers (`"since": 12`). A string value is ignored and the default is used.
- `env_set_active` takes `{"environment": null}` to clear the active environment; the schema declares the argument as a string.
- `request_cancel` takes the request id given to `request_send`, the word `last`, or `run:` followed by a collection id to cancel a `collection_run`.
- `snippet_generate` languages: `curl` (default), `raw-http`, `fetch`, `python`, `go`, `rust`, `powershell`, `node-axios`. Variables stay unresolved in the output. See [Code snippets](/guide/code-snippets).
- `collection_run` with `iterations` omitted runs once per data row, or once without data. See [Collection runner](/guide/collection-runner).

## MCP server (planned)

::note
There is no MCP server today. `postguy-cli mcp` is not a subcommand: the CLI prints its usage and exits with code 2. The feature is tracked as `planned` in [Feature status](/reference/feature-status).
::

The plan, from the project rules:

- It is a stdio server started as `postguy-cli mcp`, over the same tool table as above.
- It is opt-in: the app, the CLI and the installers never start it or register it with any client. The Windows installer explicitly registers no MCP server.
- Any future network transport would be off by default, bound to loopback and token-authenticated.

Until it ships, an agent can use `postguy-cli tools --json` to learn the schemas and `postguy-cli call` or `run --script` to run them.
